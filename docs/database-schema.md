# Database Schema

This document summarizes the current OmniBot V3 database schema after CTO Review Revision 1. The detailed architecture, index rationale, uniqueness rationale, scalability review, and schema score live in `docs/database-layer-design.md`.

## Core Design

OmniBot V3 uses a shared Supabase PostgreSQL database with organization-scoped rows. The organization root is `organizations`; business-owned records use `organization_id` and Row Level Security.

Strict organization isolation is reinforced with composite organization-safe foreign keys such as `(customer_id, organization_id)` and `(conversation_id, organization_id)`, not only standalone IDs.

Backend and database terminology must use organization language. The approved database boundary is `organization_id`. UI and customer-facing copy may use "brand" for Instagram fashion sellers, but schema and repository contracts must use "organization".

## Tables

### organizations

Organization root for each seller account. Stores name, slug, status, default currency, timezone, settings, and metadata.

### users

Application profile linked 1:1 with Supabase `auth.users`.

### memberships

Connects users to organizations with role and status. Supports owner/admin/manager/agent/viewer access models.

### customers

CRM customer profile. Stores display details, status, `lead_stage`, AI-inferred `purchase_stage`, lead score, lifetime value, order count, engagement timestamps, tags, profile data, and metadata.

### customer_identities

Provider identity table for WhatsApp, Instagram, Facebook, website, email, and future channels. Replaces provider-specific columns previously stored directly on `customers`.

Fields include:

- `organization_id`
- `customer_id`
- `provider`
- `provider_user_id`
- `provider_username`
- `provider_phone`
- `metadata`

### conversations

Conversation container by channel and customer. Supports state, status, handoff status, priority, assignment, summary, last message, `last_ai_response_at`, and `last_customer_response_at`.

### messages

Immutable message history. Supports inbound/outbound messages, customer/AI/human/system senders, external message IDs, webhook retry protection, provider payloads, delivery timestamps, and message status.

### products

Normalized product catalog rows. Includes normalized name, SKU, pricing, inventory quantity, reserved inventory, low-stock threshold, attributes, and metadata.

### faq_entries

Normalized FAQ rows. `normalized_question` is generated by database trigger from `question` and deduplicated per organization.

### message_ai_analysis

Structured AI analysis for a message: intent, confidence, sentiment, product interest, budget signals, purchase stage, lead score delta, and extracted entities.

### ai_interactions

AI cost and performance ledger. Tracks provider, model, tokens, latency, cost estimate, request ID, status, and errors.

### ai_feedback

General AI feedback table for ratings, reasons, and corrected responses.

### merchant_feedback

Training-data table for merchant-edited AI responses. Stores original response, edited response, feedback type, and AI interaction reference.

### conversion_events

Event-sourced conversion timeline for core commerce milestones such as lead creation, product interest, payment link sent, payment completed, won, and lost.

### lead_events

Sales funnel event stream. Tracks lead-stage progression and events such as lead creation, product interest, price discussion, payment requested, payment sent, payment completed, won, and lost.

### organization_usage_daily

Daily usage rollup for future SaaS billing. Tracks messages, AI requests, token usage, and estimated AI cost.

### automation_events

Follow-up and automation foundation. Supports scheduling, execution state, idempotency, payloads, and errors.

### subscription_plans

Static SaaS plan definitions. Initial plans are Starter, Growth, and Pro with monthly message, AI request, and token limits.

### organization_subscriptions

Current organization subscription state. No payment provider integration is modeled yet.

## Key Distinctions

### purchase_stage vs lead_stage

`purchase_stage` is AI-inferred buyer psychology. It describes what the AI thinks the buyer is doing: awareness, interest, consideration, intent, purchased, lost, or unknown.

`lead_stage` is CRM pipeline state. It describes the operating state of the sales process: NEW, ENGAGED, INTERESTED, PAYMENT_SENT, WON, or LOST.

Both exist because AI interpretation and business workflow are not the same.

## Deferred Schema

- WhatsApp integration mapping schema is deferred until channel connection and webhook ingestion are implemented. The integration module will own it.
- `audit_events` or `admin_audit_log` is deferred until sensitive admin mutations and service-role write workflows are implemented. The security/compliance module will own it.
- `knowledge_sources`, `knowledge_chunks`, and embeddings are deferred until RAG ingestion and retrieval are implemented. The knowledge/RAG module will own them.
- Billing provider mappings are deferred until a payment provider is selected and webhook handling is implemented. The billing module will own them.
